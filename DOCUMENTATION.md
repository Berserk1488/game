# Программная документация

## 1. Назначение программы

Программа реализует одноранговое сетевое приложение для игры «камень-ножницы-бумага» между двумя узлами локальной сети. Один экземпляр запускается в режиме мастера, второй — в режиме игрока. Перекомпиляция для смены режима не требуется: режим выбирается флагом командной строки.

## 2. Используемые средства сетевого программирования

Программа написана на C++ и использует программный интерфейс сокетов Беркли.

Используются системные вызовы и функции:

- `socket(AF_INET, SOCK_DGRAM, 0)` — создание UDP-сокета;
- `bind()` — связывание сокета с локальным UDP-портом;
- `sendto()` — отправка UDP-пакета на адрес партнёра;
- `recvfrom()` — получение UDP-пакета и адреса отправителя;
- `select()` — ожидание входящих данных с таймаутом;
- `close()` — закрытие дескриптора сокета.

## 3. Режимы запуска

Режим мастера:

```bash
./game --master <port>
```

Режим игрока:

```bash
./game --player <master_ip> <master_port> [local_port]
```

Если `local_port` в режиме игрока не указан, ОС автоматически выбирает свободный локальный порт.

## 4. Прикладной протокол

Протокол работает поверх UDP и добавляет те свойства, которых UDP не гарантирует: подтверждение получения, повторную отправку и обработку сообщений в правильном порядке.

### 4.1 Формат пакета

| Поле | Размер | Описание |
|---|---:|---|
| `magic` | 2 байта | сигнатура `0x4750`, позволяет отбросить чужие пакеты |
| `version` | 1 байт | версия протокола |
| `type` | 1 байт | тип сообщения |
| `seq` | 4 байта | номер сообщения отправителя |
| `ack` | 4 байта | номер подтверждаемого сообщения |
| `length` | 2 байта | длина полезной нагрузки |
| `payload` | `length` байт | строковые данные сообщения |

Многобайтовые целые поля передаются в сетевом порядке байтов.

### 4.2 Типы сообщений

| Код | Тип | Назначение |
|---:|---|---|
| 1 | `HELLO` | запрос на начало игры |
| 2 | `WELCOME` | подтверждение подключения |
| 3 | `MOVE` | ход игрока |
| 4 | `RESULT` | результат раунда |
| 5 | `ACK` | подтверждение сообщения |
| 6 | `ERROR` | ошибка протокола |
| 7 | `BYE` | завершение игры |

## 5. Механизм подтверждений и порядка

Для обмена используется алгоритм `stop-and-wait`.

Отправитель:

1. Формирует сообщение с текущим номером `seq`.
2. Отправляет сообщение через `sendto()`.
3. Ожидает `ACK` с полем `ack == seq`.
4. Если подтверждение не получено за `800 ms`, повторяет отправку.
5. После `8` неудачных попыток считает партнёра недоступным.

Получатель:

1. Принимает пакет через `recvfrom()`.
2. Проверяет сигнатуру, версию, тип и размер.
3. Сравнивает `seq` с ожидаемым номером.
4. Если номер совпадает, обрабатывает сообщение и отправляет `ACK`.
5. Если номер меньше ожидаемого, считает сообщение дублем: повторно отправляет `ACK`, но не меняет состояние игры.
6. Если номер больше ожидаемого, сообщение игнорируется как пришедшее вне очереди.

Такой механизм обеспечивает обработку игровых сообщений в правильном порядке и защищает состояние игры от повторной обработки дублей.

## 6. Структуры данных

### 6.1 `Packet`

```cpp
struct Packet {
    uint8_t type;
    uint32_t seq;
    uint32_t ack;
    std::string payload;
};
```

Структура хранит уже разобранное прикладное сообщение. Для передачи по сети она сериализуется в бинарный формат. Такой подход выбран, чтобы не зависеть от выравнивания структур компилятором и явно преобразовывать многобайтовые поля в сетевой порядок байтов.

### 6.2 `sockaddr_in`

Используется стандартная структура адреса IPv4 из Berkeley sockets. Она хранит IP-адрес и номер UDP-порта партнёра.

### 6.3 `UdpPeer`

Класс-обёртка над UDP-сокетом. Отвечает за:

- отправку и приём сырых пакетов;
- сериализацию и разбор сообщений;
- отправку `ACK`;
- надёжную отправку с повторными попытками;
- приём сообщений с контролем порядка.

## 7. Логика игры

1. Master запускается и ожидает `HELLO`.
2. Player отправляет `HELLO`.
3. Master фиксирует адрес первого игрока и отправляет `WELCOME`.
4. В каждом раунде player отправляет `MOVE`.
5. Master вводит свой ход, вычисляет результат и отправляет `RESULT`.
6. После трёх раундов master отправляет `BYE`.

## 8. Ограничения реализации

- Поддерживается только один подключённый игрок.
- Поддерживается IPv4.
- Протокол ориентирован на локальную сеть.
- Одновременно обрабатывается только один игровой сеанс.
